# Agent 优势区实验 Round2（AZ2，2026-10-12，语料 v2 · 100 篇 · chunking 修复后）

## 先报告两个基础设施发现（比实验结论更重要）

**1. splitter 中文分句 bug（已修，commit 见 git log）**
原 `SENTENCE_PATTERN` 只认英文句读 `.!?`，纯中文段落被当成一个"句子"，单句超长时整篇文档落进同一个
chunk——**全库实为"文档级检索"伪装成 chunk 级检索**。此前所有"混合查询召回鲁棒"的观察都是该 bug 的
产物。同修 `preprocessText` 压平换行导致表格/列表行黏连的问题。修复后 100 篇语料 = 258 chunks
（修复前 46 篇才 70 chunks，F 区长文档 1 chunk → 13-15 chunks）。

**2. "埋点藏数字"机制被证伪**
分块修复后用 9 个口语化埋点做原文探针：qwen text-embedding-v3 + rerank 下全部排进 top10 前三，
**深埋事实藏不住**。据此放弃措辞类机制，改用与 embedding 强弱无关的结构性机制——**slot 容量**：
top5 只有 5 槽，所需 chunk 数 > 5 时单次检索数学上不可能全覆盖。

## 结论

**1. slot 容量机制成立，但它是"一堵墙"而不是"分水岭"**：AZ06-08（6-8 chunk 需求）三臂全败——
预算=3 的 C 也覆盖不了 6 个主题（模型自发查询的配对效率低于人工探针配对）。C 的价值是**退化最优雅**：
AZ07 5/6 vs B/A 的 4/6，且缺项全部诚实申报（AZ08"三次检索仍未找到，基于已有信息作答"）。

**2. 干净的 B 败 C 胜案例存在：AZ01**（C 4/4，B 3/4，A 2/4）——4 文档事实，C 的多轮检索能补，
B 的单查 5 槽装不下。但这类"刚好卡在 B 能力之外、C 预算之内"的窗口很窄：6 事实以上 C 也过不了。

**3. 分块修复让基线变强了**：AZ03 上 A 翻案（chunk 级检索让"办公设备"条款独立成块、可被精确命中）。
修复检索基础设施对基线的增益 ≥ 对 agent 的增益——**基础设施优先于架构差异**再次应验。

**4. judge 可信度是当前评测最大的短板**（Round1+Round2 连续坐实）：同实质答案不同 verdict、
奖励编造的完整感、惩罚诚实的缺口申报。跨臂结论必须人工抽检；中期应改 pairwise judge。

## 工程含义

- 路由规则更新：**证据宽度 > 4-5 chunk 的题，当前没有任何臂能全对**——应做"部分回答 + 缺口申报"，
  而不是硬答；C 是唯一行为正确的臂（诚实申报），这本身是 agent 的审计价值。
