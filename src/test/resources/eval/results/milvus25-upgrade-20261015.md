# Milvus 2.3.4 → 2.5.4 升级验证（2026-10-14/15）

## 一、升级内容

向量层迁移到 `MilvusClientV2`（旧 API 在 2.5.4 无稀疏字段/BM25 Function），服务端原生混合检索：
`text`(chinese analyzer) + `sparse`(BM25 Function 生成) + `dense`，融合用 `RRFRanker(60)`。
`rag.search.hybrid.provider`：`milvus`（默认）/ `local`（手写 BM25 对照，保留）。

同时修掉一个入库瓶颈：逐篇 flush 会让每个 growing segment 反复封存并触发 compaction，
实测把入库压到 **7 篇/分**；改为可配置（`rag.vector.flush-on-insert=false` 用于批量）+ 收尾显式 flush 后，
**404 篇 5 分钟内完成**（>80 篇/分，10 倍以上）。

## 三、根因诊断（已定位到具体机制）

**① Milvus 稀疏腿无法匹配 `YC-XX-YYYY-NNNN` 形式的业务编号**（直接 REST 取证，绕过应用）：

| 查询 | 稀疏腿结果 |
|---|---|
| `MTP13-CN`（字母+数字+单连字符） | ✅ 命中正确条款（score 11.06） |
| `补卡` / `固定资产保修期限登记表` / `整机 36 个月` | ✅ 命中正确块 |
| **`YC-HY-2026-0002` / `YC-HY-2026-0003` / `YC-JJ-2026-0004`** | ❌ **三个不同编号返回同一条、同分数 6.88** → 查询中的区分性 token 未参与匹配 |
| `2026-0002` | ❌ 无结果 |

**推论：这不是 RRF 融合稀释，而是稀疏腿本身取不到该块** → 提高稀疏权重（`WeightedRanker`）**无效**。
应用侧 K 从 10 扫到 50，目标块**均不可召回**。

**② 但 local provider 的 agent 多跳臂同样掉到 0/5**（升级前 2-3/5）→ 多跳下滑**不单独归因于 Milvus**。
两个候选原因，需下一步隔离：
- 本次把 `相似度` 从 agent 工具输出中移除（因两条 provider 分数语义差十倍、不可比），
  这可能改变了 agent 的覆盖性自检行为；
- n=5 且 MH205/206/207 是**同一台设备问三个字段**（选题缺陷），单题波动被放大。

## 四、结论与下一步

1. ✅ **升级本身可用**：普通中文检索无回归（20/20），迁移与基础设施改动正确、可回滚（旧 2.3.4 容器与卷保留）。
2. ❌ **"以 Milvus 原生 BM25 替代手写词法通道"在业务编号精确检索上不成立**——BM25 的分词对
   `YC-XX-YYYY-NNNN` 这类编号失效。成熟且确定的替代是**标量字段 + 表达式精确过滤**
   （清单早已指出该能力在 2.3.4 上即可用）：把业务编号抽成标量/数组字段，查询含编号时走 `expr` 过滤。
   **这是本升级唯一未闭环的部分。**
3. ⏭ 下一步（按序）：
   a. 隔离多跳下滑归因：把显示改动作为变量单独复测（或恢复分数用 rank 表达）；
   b. 修选题缺陷：MH 改覆盖 5 个**不同**资产；
   c. 实施标量字段精确过滤，复跑 `probe_exact_id.py` 与 MH；
   d. 复测后再决定 `local` 通道是否可删。
