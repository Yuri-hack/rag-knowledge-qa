# Milvus 2.3.4 → 2.5.4 升级验证（2026-10-14/15）

## 一、升级内容

向量层迁移到 `MilvusClientV2`（旧 API 在 2.5.4 无稀疏字段/BM25 Function），服务端原生混合检索：
`text`(chinese analyzer) + `sparse`(BM25 Function 生成) + `dense`，融合用 `RRFRanker(60)`。
`rag.search.hybrid.provider`：`milvus`（默认）/ `local`（手写 BM25 对照，保留）。

同时修掉一个入库瓶颈：逐篇 flush 会让每个 growing segment 反复封存并触发 compaction，
实测把入库压到 **7 篇/分**；改为可配置（`rag.vector.flush-on-insert=false` 用于批量）+ 收尾显式 flush 后，
**404 篇 5 分钟内完成**（>80 篇/分，10 倍以上）。

| 运行 | 结果 | 判定 |
|---|---|---|
| 20 题漏斗子集（provider=milvus，基线） | **20/20** | ✅ **无回归**（与升级前一致；已核验每题都有 10 条真实检索记录，非缓存回放） |
| 20 题漏斗子集（provider=local，基线） | **20/20** | ✅ |

## 三、根因诊断（已定位到具体机制）

**① Milvus 稀疏腿无法匹配 `YC-XX-YYYY-NNNN` 形式的业务编号**（直接 REST 取证，绕过应用）：

| 查询 | 稀疏腿结果 |
|---|---|
| `MTP13-CN`（字母+数字+单连字符） | ✅ 命中正确条款（score 11.06） |
| `补卡` / `固定资产保修期限登记表` / `整机 36 个月` | ✅ 命中正确块 |
| **`YC-HY-2026-0002` / `YC-HY-2026-0003` / `YC-JJ-2026-0004`** | ❌ **三个不同编号返回同一条、同分数 6.88** → 查询中的区分性 token 未参与匹配 |
| `2026-0002` | ❌ 无结果 |

**推论：这不是 RRF 融合稀释，而是稀疏腿本身取不到该块** → 提高稀疏权重（`WeightedRanker`）**无效**。
应用侧 K 从 10 扫到 50，目标块**均不可召回**。

**② 但 local provider 的 agent 多跳臂同样掉到 0/5**（升级前 2-3/5）→ 多跳下滑**不单独归因于 Milvus**。
两个候选原因，需下一步隔离：
- 本次把 `相似度` 从 agent 工具输出中移除（因两条 provider 分数语义差十倍、不可比），
  这可能改变了 agent 的覆盖性自检行为；
- n=5 且 MH205/206/207 是**同一台设备问三个字段**（选题缺陷），单题波动被放大。

## 四、结论与下一步

1. ✅ **升级本身可用**：普通中文检索无回归（20/20），迁移与基础设施改动正确、可回滚（旧 2.3.4 容器与卷保留）。
2. ❌ **"以 Milvus 原生 BM25 替代手写词法通道"在业务编号精确检索上不成立**——BM25 的分词对
   `YC-XX-YYYY-NNNN` 这类编号失效。成熟且确定的替代是**标量字段 + 表达式精确过滤**
   （清单早已指出该能力在 2.3.4 上即可用）：把业务编号抽成标量/数组字段，查询含编号时走 `expr` 过滤。
   **这是本升级唯一未闭环的部分。**
3. ⏭ 下一步（按序）：
   a. 隔离多跳下滑归因：把显示改动作为变量单独复测（或恢复分数用 rank 表达）；
   b. 修选题缺陷：MH 改覆盖 5 个**不同**资产；
   c. 实施标量字段精确过滤，复跑 `probe_exact_id.py` 与 MH；
   d. 复测后再决定 `local` 通道是否可删。

# 🔬 同语料对照：混合检索到底带来了什么（2026-10-15，408 篇语料）

问题：升级到混合检索后正确率更高了吗？——**分任务看，答案不同。**

| 配置（同 408 篇语料） | 漏斗 20 题 | 多跳 agent MH203-207 | 精确编号排名 |
|---|---|---|---|
| **混合检索**（milvus 原生 dense+BM25+RRF+标量过滤） | 19/20 | **3/5, 3/5, 4/5** | **1, 1, 1** |
| 混合检索（local 手写词法对照） | — | **3/5, 3/5** | — |
| **纯稠密**（`rag.search.hybrid.enabled=false`） | **19/20**（逐题相同） | **1/5** | 2, 2, 7 |

## 结论

1. **普通问答：混合检索零增益。** 20 题漏斗 19/20 vs 19/20，**逐题完全相同**。
2. **精确编号：稠密也能取到**（排名 2/2/7，K≥7 即可作答）——因为**词法匹配实际是 cross-encoder reranker 完成的**
   （重排阶段直接读 query 与 chunk 文本）；稠密召回只需把该块放进候选池。
   混合检索的价值仅是**把排名从 2/7 提到 1**（边际改善，不改变可答性）。此前"稠密无法匹配编号"的推断不成立。
3. **多跳（agent）：词法通道带来显著增益** —— 3-4/5 vs **纯稠密 1/5**。
   但增益来自"**有一条词法通道**"这件事：Milvus 原生（3/3/4）与手写 local（3/3）等价。
   ⚠️ 注意：纯稠密只跑了 **1 次**（n=5 题），虽与混合臂 5 次运行（3,3,4,3,3）差距明显，仍建议补跑 2 次确认。

## 对升级决策的含义

- **"把手写词法通道换成 Milvus 原生"这个升级，在正确率上是中性的**（多跳等价、漏斗相同、度量小幅提升但混淆于语料变化）。
- 它买到的是：**少一套自维护代码**、服务端统一融合、以及 schema 层面更强的能力（BM25/标量过滤/将来元数据过滤）。
- **它没有买到正确率提升**——真正提升多跳的是"有词法通道"这个架构选择，而这个结论在升级前用手写通道就已经成立。

# 🔬 K × 邻域扩展 六组扫描（2026-10-15，408 篇语料，N 固定 50）

## 漏斗（20 题，baseline）

| K | neighbor=0 | neighbor=1 | avgToken (0 / 1) |
|---|---|---|---|
| 10 | 18/20 | 18/20 | 3,490 / 3,600 |
| **20** | **19/20** | **19/20** | 5,831 / 5,943 |
| 50 | 19/20 | 19/20 | 11,466 / 11,521 |

**邻域对漏斗无增益（也不伤，token +2~3%）→ 漏斗的瓶颈是 K 本身，不是单块自足性。**

## 多跳（5 题，agent 侧 N50/K30）

| 配置 | 分数 | avgToken |
|---|---|---|
| K=10 / 邻域 | 4/5 | 39,906 |
| K=20 / 无邻域 | 3/5 | 71,318 |
| **K=20 / 邻域** | **5/5**（5 题全 2/2） | **53,824** |
| K=50 / 邻域 | 2/5 | 52,509 |

## 结论与已落盘的默认值

1. **邻域扩展在多跳上明确有效**：同 K=20 下 3/5 → **5/5**，且 token **降 25%**（一次检索给足上下文 → agent 少重试）。
   这是"邻域扩展"设计意图的实证：治的是**单块信息不自足**，不是召回不足。
2. **"K=20 + 邻域"优于"K=50"**：漏斗同为 19/20（token 5.9k vs 11.5k），多跳 5/5 vs 2~4/5。
3. **已落盘默认值**（`application.yml`）：
   `rag.search.top-k=50`、`top-ratio=20`、`neighbor-window=1`、`neighbor-top-hits=5`、`neighbor-max-total=30`；
   `rag.agent.search.top-k=50`、`top-ratio=30`。

## 保留（正在确认）

- 多跳每组**单次采样**（n=5 题）；K=50/邻域 的 2/5 非单调，可能是"K 已大时邻域变噪声"或方差；
- 已发起确认实验：K=20 邻域开/关各 **3 次**、K=50/邻域 2 次，用于确认那 +2 的稳定性；
- 邻域按 chunkIndex 相邻，**不保证同小节**（跨小节边界的邻块可能属别章）。

# ❌ 更正：邻域扩展的"+2"未复现（2026-10-15 确认实验，8 次运行）

上文"结论二：邻域扩展在多跳上明确有效（3/5→5/5）"**是单次采样造成的假阳性，现已推翻。**

## 分数序列（K=20，同配置重复）

| 组 | 各次总分 | 合计 | avgToken 均值 |
|---|---|---|---|
| K=20 / window=0 | 4, 4, 3, 3 | **14/20 (70%)** | ~50.2k |
| K=20 / window=1 | 4, 3, 3, **5** | **15/20 (75%)** | ~46.5k |
| K=50 / window=1 | 3, 3, 2 | 8/15 (53%) | ~53.3k |

- **分布高度重叠**：n1 的 5/5 是孤立高位，其余三次与 n0 同区间；
- **逐题双向翻转**：n1 在 MH205(1→2)、MH207(2→4) 有增益，但在 MH203(4→3)、MH206(3→2) 有损失；
- 净差 1/20，在 n=4×5 下远低于可检出阈值 → **判为噪声**。
- K=50/邻域 三次 3,3,2 → 2/5 只是该组下尾，但 **K=50 在多跳上确实更差**（53% vs 70-75%），与"漏斗同分但 token 翻倍"一致。

## 处置（已落盘）

1. **`neighbor-window` 改回 `0`**（能力保留、可配置、默认关闭），并在 yml 注释里写明推翻原因；
2. **保留 `top-ratio=20`**（漏斗 19/20 与 K=50 持平、token 约一半；多跳 70-75% 优于 K=50 的 53%）；
3. 若将来要判定邻域是否有效，**必须扩大样本**：把多跳题集从 5 题扩到 20-30 题，或每题重复 5-10 次取通过率——而不是比单次总分。

## 更重要的方法论影响（对所有历史多跳结论）

**agent 多跳臂在同一配置下跨度可达 3~5/5（±1 题）。** 因此本项目此前所有基于 MH203-207 的**单次**结论都应带 ±1 题误差棒，包括：
