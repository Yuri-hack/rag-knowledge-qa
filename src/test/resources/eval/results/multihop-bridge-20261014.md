# 数据键桥接多跳：agent 的第一个结构性优势场景（2026-10-14）

## 一、要找的是什么

前几轮的结论是：多主体/多事实/宽聚合题都能被"调大 K"解决，因为**判别信息在问题里**。
真正需要迭代的只有一种结构：

> **答案的判别性 token 不在问题里**，必须先用第一次检索的结果去构造第二次查询。

这就是"数据键桥接"（业务编号/型号/单号 → 对应条款）。此时任何排序函数都无法选出正确的
那一条（所有候选对问题的相关度相同），**调大 K 也无解**——把全部候选塞进上下文，仍不知道该信哪一条。

## 二、v1 失败（batch5）：探针在评测前拦下了设计缺陷

v1 设计：采购通知（设备名 → 型号）+ 300 篇"按型号的保修条款"。

探针结果：**合格 1 / 丢弃 9**。两个原因：

| 现象 | 根因 |
|---|---|
| 9/10 题桥接文档取不到（死题） | 300 条条款语义全是"保修期"，把唯一的采购通知挤出 top-50 |
| 7/10 题正确条款直达（多在第 1 名） | **我造的型号泄漏了设备名 token**：`LAT5450`↔"5450"、`27UP850`↔"27UP850"、`HP-Z66-G6`↔"66/HP" |

教训：**"保修条款"这类目标文档天生与问题语义重叠**，不适合做数据键桥接；
且判别 token 必须与设备名**零词汇重叠**。

## 三、v2 设计（batch6）：资产登记表

- **A. 《2026 年新增办公设备配发通知》**：设备名称 + 使用部门 → **资产编号**（`YC-XX-2026-NNNN`）
- **B. 《固定资产保修期限登记表》**：一张 **400 行**的大表（≈58 chunks），每行「资产编号 | 整机 | 电池 | 屏幕」
- **C. 2 篇管理办法**（真实感）

为什么这是真多跳：
1. 问题的判别信息（资产编号）不在问题里，且与设备名无语义/词汇重叠；
2. 目标行只是 400 行中的一行（58 个 chunk 之一），问题无法把它捞出来；
3. 调大 K 无解：登记表全塞进上下文，仍需先知道编号才能定位那一行；
4. agent 的迭代是**结构必需**：先查通知拿编号 → 再用编号精确检索那一行。

## 四、预注册判据与筛选结果

判据（先立后测，不合格即丢弃，不按结果挑题）：

- ✅ 桥接文档《配发通知》必须出现在单次检索结果里（否则是死题，不是多跳题）
- ✅ 目标资产编号**必须不出现在任何一条检索结果的内容里**（出现即单次检索可答，非多跳）

| 结果 | 题数 | 明细 |
|---|---|---|
| 合格 | **5** | MH203 / MH204 / MH205 / MH206 / MH207 |
| 丢弃 | 5 | MH201/MH208/MH209/MH210（登记表目标行被捞出）、MH202（桥接文档取不到） |

判分事实 = **资产编号 + 期限**（编号唯一，杜绝"答错行但数字碰巧相同"的假阳性）。

## 六、失败分析（agent 那 2 题）——指向检索能力而非循环逻辑

| 题 | 失败环节 | 根因 |
|---|---|---|
| MH204 | 第一跳 ✓（正确取出 `YC-HY-2026-0002`），**第二跳 ✗** | agent 自述登记表里只看到 `YC-AF-`/`YC-QT-` 开头的行。**稠密向量检索无法精确匹配无意义编号**（编号嵌入与"含大量编号的 chunk"近乎正交）→ 需要词法/BM25/混合检索或按字段精确过滤 |
| MH207 | **第一跳 ✗** | 通知被 58 个登记表 chunk 挤出结果；agent 换了两轮措辞仍没捞到，最后诚实报告"知识库无此信息"（行为正确但未取到）。需要混合检索或对文档类型加权 |

**结论：剩下的差距是检索质量问题，不是 agent 循环的问题。** 补法明确：
1. 词法/混合检索（仓库里已有 ES/OpenSearch 配置）→ 让"按编号精确检索"可靠；
2. 或按元数据字段精确过滤（资产编号入标量字段）；
3. 更精简的 agent 配置（每次 K=10、允许多次检索）可大幅降低成本（现在 95k token 是因为每次取 50 条 × 3 次）。

## 七、成本对照（必须一并报告）

| | 通过 | avgToken | TTFT |
|---|---|---|---|
| 基线（K=50） | 0/5 | 13,498 | 2.1s |
| agent（K=50） | 3/5 | 95,069（**7 倍**） | 38.1s（**18 倍**） |

agent 在这里买到的是**能力**（基线无论怎么调参都是 0），不是效率。因此合理的产品形态是
**按题型路由**：判别信息在问题里的题走基线大 K（20/20），数据键桥接题走 agent。
