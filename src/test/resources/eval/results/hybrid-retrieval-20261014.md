# 混合检索（稠密 + BM25 词法）：实现与验证（2026-10-14）

## 一、动机（来自多跳实验的失败分析）

`results/multihop-bridge-20261014.md` 的 MH204：agent 第一跳成功取出资产编号，
**第二跳失败**——稠密向量无法精确匹配无意义 token（编号的嵌入与"含大量编号的 chunk"近乎正交）。

## 二、实现

| 组件 | 说明 |
|---|---|
| `lexical/LexicalIndexService` | 词法通道接口；`LexicalHit` 携带 BM25 分数与 `exactMatch` 标记 |
| `lexical/impl/Bm25LexicalIndexService` | 进程内 BM25 索引：字母数字串整体成词（`YC-HY-2026-0003` 为一个 token）+ 分段入索引 + 中文二元组；TTL 自动重建 |
| `KnowledgeSearchResult` | 新增 `lexicalScore`；新增 `fromChunk` 工厂 |
| `KnowledgeBaseServiceImpl` | 稠密 + 词法合并 → rerank → **精确匹配优先** → 兜底 |
| `POST /api/knowledge/lexical/rebuild` | 上传后手动重建（正常靠 TTL） |

三个关键设计决策：

1. **词法命中排在候选最前**：reranker 有 50 条硬上限（`MAX_RERANK_DOCUMENTS`），
   排尾部会在 rerank 前被截断丢掉，兜底也就无从谈起；
2. **精确匹配优先（exactMatch）**：查询含稀有 token（长度≥6 的字母数字串且 df≤3）时，
   命中它的 chunk 提到最终结果最前。理由：实测 cross-encoder 会偏好**含相似编号片段**的干扰行
   （`YC-HY-2025-0139` 分数 0.986 > 正确行 `YC-HY-2026-0002` 的 0.948），对这种查询语义排序不可靠；
3. **兜底**：词法 top-N 被 rerank 挤出时替换末尾补回（修掉了"逐条 set(size-1) 导致多条兜底互相挤出"的 bug）。

## 四、结论与下一步

1. **检索层的阻塞已解除**：MH204 那类失败（第二跳取不到编号行）在混合检索下修好。
2. **总成绩未涨，因为瓶颈转移了**：MH206/MH207 的失败不再是"取不到"，而是
   **agent 没有用编号去检索**——它有时改用 "Epson L730U 保修条款" 这类名称措辞，三跳用尽后放弃。
   即：从**基础设施瓶颈**转移到了**agent 检索策略**。
3. 因此下一步是两个明确的小改动：
   - **prompt v0.5 规则**：检索结果中出现业务编号/单号/型号，且答案需按编号查表时，
     **必须直接用该编号再检索一次**（当前只有部分轮次自发这么做）；
   - **题集去重**：当前 MH205/206/207 是同一台设备问三个字段（我的字段轮转在资产维度重复），
     应改为覆盖 5 个不同资产，降低单题策略波动的放大效应。
4. 另注：混合检索对无意义 token 的精确匹配是**通用能力**——工单号、合同号、项目编号同样受益，
   不限于本次的多跳题。
