# agent 优势区实验——复合推理与联网（2026-10-12）

> 动机：四臂对比 + 机器重判后，"agent 优势很小"成为诚实现状（简单题负优势、S01 退役）。
> 本实验对最后两个假设的优势区做定向测试：**多步复合推理**与**范围外+联网**。
> 题集：qa.json 新增 R01-R03（compound_reasoning，分母口径见 meta）；结果文件 `results/r-*.json`、`w01-agent-search-*.json`。

## 实验一：3 步复合推理（基线 vs 单发+prompt vs agent）

| 题 | 推理链 | 基线 | B 单发 | agent（bug口径1条/次） | agent（修复后5条/次） |
|---|---|---|---|---|---|
| R01 P5司龄4年已休6天含1法定节假还能休几天（8+1=9→实休5→**4天**） | 检索×2+规则+算术 | ✓ 2.2k tok | ✓ 6.2k | ✓ 6.4k | ✓ 11.9k |
| R02 法定节假日加班8h选调休能换多少+有效期（1:3→**24小时**；**3个月**） | 同文档双跳+算术 | ✓ 2.3k | ✓ 10.3k | ✓ 5.2k | ✓ 10.9k |
| R03 航班取消改签费报销+垫付上限（钩子：差旅§5→绿色通道，**5000/事前总监同意**） | 跨文档 2 跳 | ✓ 2.1k | ✓ 7.4k | **✗ 0/1** | ✓ 14.6k |

**结论：复合推理不构成 agent 优势区**——基线 3/3 全对（qwen-plus 单发即可完成"检索+规则+算术"三段），
agent 修复口径后也 3/3，但每次成本 5-7 倍（11-15k vs 2.1-2.3k tokens）。

**重要更正（2026-10-12 晚，trace 定罪）**：agent 首跑 R03 ✗ 的根因**不是**下文最初归因的 400 字符截断，
而是当时工具被误设 `topRatio=1.0`——该参数在 `computeTakeCount` 里是"绝对条数"语义，1.0 = **每次搜索只返回 1 条**。
trace 证据：三次检索全部"共 1 条"，绿色通道文档从未进入 agent 视野。改为 `topRatio=5.0` 后复验 3/3（`r-agent-v2-*.json`）。
修复后 agent 成本还进一步上涨（5 条/chunk × 多步累积）。

### R03 首跑失败的完整因果链（trace 定罪版）

1. 误设 `topRatio=1.0` → 每次搜索只回 1 条（本意是"比例100%"，实际是"绝对1条"）；
2. 模型三次查询的措辞都密集命中《差旅费报销制度》钩子 chunk → 每次看到的都是同一片段；
3. 绿色通道文档从未出现在工具结果里 → 模型如实报告"全文未出现垫付限额"，预算烧尽后诚实拒答（未编造）。

原"400 字符截断切掉 5000"的假说**未被证实**（模型根本没见过该文档的 chunk）。
截断本身已于同日移除（512→400 仅省 6-10% token，却系统性砍 chunk 尾部"文字版"数字行；
终态配置 `(topK=10, topRatio=0.5)` 与基线单次检索逐字节等价，见 prompt-changelog 三次订正）。

### 终态配置下的 MA01 对比（重要：又一处优势收敛）

`(10, 0.5)` + 完整 chunk 终态复验（`tool-final-*.json`，2026-10-12，v1.1 语料 + temp=0）：

| | facts | tokens |
|---|---|---|
| agent | 4/5（缺"总部8天"） | 17,713 |
| 基线 | **4/5（缺同一个"总部8天"）** | 3,477 |

四臂时代"agent 4/5 vs 基线 2-3/5"的 MA01 优势，在 v1.1 语料 + temp=0 + 检索对齐后**收敛为同分**（agent 贵 5 倍）。
与 S01 退役同一模式：**每修好一层基础设施（语料锚点/温度/检索口径），agent 的架构补偿价值就被侵蚀一块**。
multi_aspect 是否仍有差异，需要更多题目确认（当前 n=1）。

两个教训：
1. **修检索口径前必须读截断函数的语义分支**——`topRatio=1.0` 这个直觉上"100%"的值实际是"1条"，一行修复引入了新 bug；
2. **"agent 比 baseline 差"的数据必须先排除口径污染再解释**——R03 首跑的"agent 连基线都不如"是人为 bug，
   修复后打平（但成本仍 5-7 倍）。trace/debug 抓取工具调用是定罪的唯一方式，答案文本会撒谎，调用轨迹不会。

## 实验二：范围外问题 + 联网搜索（W01）

`ask()` 的 `enableSearch` 从硬编码 false 改为独立开关 `tongyi.agent-enable-search`（默认 false，
不挂 ragModelConfig——基线流式链路共用它，避免误开）。

开启后跑 W01（今年国庆怎么安排）：**没有发生联网**——agent 三次检索预算烧尽后高质量拒答
（指明知识库未覆盖、建议查 OA/行政部，脚注明确标注"历年惯例"）。D4 记录的"enableSearch 与
tool calling 冲突"坐实为**静默失效**：并存时搜索被忽略，不报错。

推论：needs_web 要成为 agent 的真实优势区，联网必须**做成工具**（web_search Tool，走同一预算/轨迹管理），
而不是开 enableSearch 参数——这也是 D7 的现成设计题。

## 汇总：agent 优势区地图（截至 D6）

| 场景 | 结构性差异 | 证据 |
|---|---|---|
| 多轮指代/跨轮聚合 | 基线无状态，结构为零 | D6：不改写 2/7 vs 改写 7/7 |
| 检索+规则+算术复合 | 无——基线单发可完成，agent 打平但贵 5-7 倍 | 本实验：双方 3/3，tokens 2.1-2.3k vs 10.9-14.6k |
| 跨文档钩子 | 无——rerank+完整 chunk 足够 | 本实验 R03：修复口径后基线 ✓ agent ✓ |
| 范围外联网回答 | 有，但需先把联网做成工具 | 本实验二：enableSearch 静默失效 |
| 单轮事实题 | 负优势（贵 3 倍、还略差） | 四臂：22/25 vs 24/25 |

**定位修正**：agent 的价值不是"更准的 QA"，而是"能接动作、能带状态、能留审计痕迹的架构"。
它的优势区 = 基线结构缺失区（多轮 ✓、外部动作待做、guardrail 待做），且要警惕 agent 特有的
新失败面（截断/预算/工具误用）——每加一个动作，就要配一个对应的完整性保障。
