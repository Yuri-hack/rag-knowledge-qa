# D6 · 多轮记忆与会话——设计与验证（2026-10-12）

## 架构

```
GET /api/chat/rag/stream?question=...&sessionId=s1&rewrite=true
 └─ ChatOrchestrationServiceImpl.chatStream
     ├─ ① ChatSessionStore.load(sessionId)          Redis list，最近 3 轮，TTL 120min
     ├─ ② QueryRewriteService.rewrite(问题, 历史)    qwen-plus temp=0（prompt 冻结于 application.yml）
     │     "那病假呢？" → "上海子公司病假每年有几天？"
     │     失败降级原问题，绝不抛异常
     ├─ ③ route(standalone query)                    精确缓存 / 语义缓存 / 意图路由 / 检索 全部用改写后 query
     └─ ④ ReactorUtils.writeAnswerDetached           回答完成后追加会话历史（记原始问题）
           与客户端断连无关（cache()+侧车道，同缓存回写解耦机制）
```

关键决策：
- **改写只在记忆层、带完整上下文做一次**——这是"缓存 key 层不做 LLM 归一化"（D6 前置修复）的另一半：
  无上下文的改写会击穿缓存 key；带上下文的改写产出的 standalone query 天然是合法缓存 key。
- **历史存原始问题**（非改写后），下一轮改写看到的才是真实对话。
- `sessionId` 空 = 无记忆单轮，请求行为与 D6 之前完全一致（评测基线不受影响）。
- agent 端点暂不接记忆（多轮 demo 与用例都在基线路径；agent 的记忆=消息历史注入，留作 D7 顺路项）。

## 可证伪验证

qa.json 新增 MT01-MT07 七条多轮用例（跨主体指代：子公司 P4=7/P5=10/病假10工作日/调休1:2·1:4/6个月 vs 总部 P4=5/1:1.5/1:3/3个月——裸 query 命中总部数字即错）。

| 模式 | 结果 | 说明 |
|---|---|---|
| `--rewrite false` | **2/7** | MT04/MT06 裸 query 检索恰好容忍；MT01/02/03/05/07 全部命中错误主体（那P5呢→总部8天、法定节假日→总部1:3） |

## 两个真实教训（面试叙事点）

1. **首轮冷启动**：追加钩子最初挂在"历史非空"分支里——第一轮历史必然为空 → 钩子不挂 → 第一轮答案永远不入库 → 会话永远是空记忆，且日志一行不报错（只是永远 0 轮）。
   教训：**会话的常态入口是首轮**，写路径必须无条件挂，读路径才看历史是否为空。
2. **毫秒级竞态**：detached 追加在回答完成后的毫秒级落库，eval 脚本收到 finished 立即发下一轮，`load` 输给 `RPUSH` 概率极高（15ms 量级）。
   处置：eval 轮间加 1s。真实用户打字间隔秒级，不受影响；若未来有毫秒级连发的客户端，需改为"追加完成前拒绝下一轮"或同步追加。
